## Fait : un signal FORT du LLM doit s'appuyer sur le paquet observé
- **La cause :** deux « preuves » ne disaient rien du paquet.
  - Pour certifi, le LLM a recopié un passage du RAG (« PTH file… payload stored in chunks in DNS
    records »).
  - Pour idna, il a écrit « non reconnu dans la base de sécurité ».
  - La politique compte tout signal FORT : un seul suffisait à mettre la version à revoir.
- **La règle, dans le code** (`plateforme/pipeline/llm.py`) :
  - Un signal FORT du LLM reste FORT seulement si son extrait recoupe ce que le paquet a montré :
    - une ligne, un fichier ou un domaine relevé par les contrôles ;
    - ou un élément du rapport de sandbox (DNS, connexion, fichier, leurre, processus).

    Un chemin abrégé compte aussi (« ~/.aws »).
  - Sinon, il **redescend à MOYEN**, marqué `non_ancre` dans la preuve. C'est le cas d'un passage
    du RAG recopié, d'une phrase vague, ou du seul nom ou de la seule version du paquet.
  - Le signal reste visible sur la fiche. L'explication du LLM ne change pas.
- **Le principe tient :**
  - c'est le code qui décide du niveau, et le LLM ne peut toujours ni approuver, ni bloquer, ni
    abaisser un autre signal ;
  - il perd seulement le pouvoir de mettre seul une version « à revoir » sans preuve tirée du
    paquet ;
  - un passage du RAG est une donnée sur d'**autres** paquets : il ne prouve rien sur celui-ci.
- **Ce qui ne change pas pour la démo :**
  - la 1.2 reste bloquée par la statique (exfiltration) et la sandbox (leurre lu) ;
  - la 1.3 reste « à revoir » par la statique (`domaine_suspect`), sans compter sur le LLM.
- 7 tests neufs, vus rouges avant le code :
  - les deux cas réels, certifi et idna ;
  - le nom et la version du paquet cités seuls ;
  - quatre vraies preuves qui restent FORT.

  Trois mutations vues rouges : la règle sautée, le nom et la version acceptés comme preuve, et le
  chemin abrégé non reconnu. Suite complète : 518 verts, 13 sautés.
