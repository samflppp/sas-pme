# Point B (Mouabd19) — M1 : veille PyPI + OSV — 2026-10-10

## Fait
- **`plateforme/pipeline/veille.py`**, appelée au **début de chaque tour de `traiter()`**. Rien ne
  change chez A : la tâche de fond appelle toujours `traiter(base, dossier=...)`.
  1. **Nouvelles versions.** Pour chaque paquet PyPI déjà au catalogue, la version stable la plus
     haute, si elle est plus récente que toutes les versions connues, entre **en attente**, avec
     l'acteur `veille`. Le délai part de sa publication sur PyPI. C'est la version qui attend dans
     la file pour l'étape 2 de la démo.
  2. **Statut PyPI.** Une version en attente retirée de PyPI (yanked, sans fichier, ou paquet
     supprimé) passe **bloquée**, avec le signal `retiree_pypi`.
  3. **OSV** (`POST /v1/querybatch`, réglable par `SAS_OSV_URL`). Une version en attente connue
     malveillante (`MAL-…`) passe **bloquée**, avec le signal `malveillant_osv`. Sa preuve porte
     `ref`, `url` (osv.dev) et `extrait`. Une simple faille (GHSA, PYSEC) ne bloque pas.
- Chaque blocage par la veille écrit un signal `VEILLE`/`BLOQUANT` (source structurée), un verdict
  (son id est sur la fiche) et un changement d'état. Le journal reste intègre.
- Si PyPI ou OSV est injoignable, rien n'est bloqué : le paquet suivant avance, et on réessaie au
  tour suivant. Une veille en erreur n'empêche pas l'analyse.
- 205 tests passent. Le code a été cassé quatre fois pour voir les tests au rouge : retraits
  ignorés, OSV ignoré, pas la plus haute version, veille non appelée.
- Non vérifié en vrai : mon environnement de travail n'a pas accès à `api.osv.dev`. La plateforme
  AWS, elle, y a accès.

  automatiquement : c'est la révocation du M2.
