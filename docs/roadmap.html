sas-pme — Roadmap du MVP

Hackathon Track 3 · A = Sam (plateforme web) · B = Mouabd19 (pipeline + IA) · C = STEUSSO (réseau + passerelle) · H0 = début de la roadmap · ~30 h
Vos serveurs n'installent que ce qu'on a vérifié. Les serveurs sensibles de la PME n'ont pas Internet : ils prennent pip et npm dans une passerelle sans Internet, qui ne reçoit que des versions attendues 3 jours, analysées localement (code, sandbox, LLM + RAG) et signées par une plateforme agréée, la seule machine connectée. Objectif : un MVP démontrable, pas plus.

Principes non négociables

Les serveurs ne parlent jamais à Internettout passe par la passerelle, qui ne parle qu'à la plateforme
Le code décide, l'IA alertele LLM ou un article peut monter un risque, jamais approuver
Un texte lu n'est pas un ordrecode, changelog, article, RAG : des données ; sortie du LLM validée par schéma
Rien sans signaturela passerelle refuse un manifeste mal signé, un hash différent, un nonce rejoué
Tout localLLM, RAG, sandbox sur la plateforme ; aucun service d'IA cloud
Journal inaltérableappend-only, chaîné par hash

3version piégée bloquée : la sandbox l'a vue appeler son serveur et lire un faux jeton ; le LLM l'explique en citant un cas du RAG

Comment on travaille, et les sauvegardes

Branches : pourquoi pas trois branches longues

Trois branches longues divergent en quelques heures : chaque fusion devient une crise, et chacun code contre une version périmée du travail des autres — c'est « travailler dans le vide ».

Retenu : main comme tronc + une branche courte par tâche (a/…, b/…, c/…), vivante 1 à 3 h, fusionnée par PR dès que les tests passent. Chacun repart de main à chaque tâche et voit le travail des autres en quelques heures. Pas de conflit : chacun possède ses dossiers.

Stubs

Chaque interface de docs/contrats.md existe dès M0 en faux : B code le pipeline avant la sandbox de C, A affiche une fiche avant le verdict réel de B. Le vrai remplace le faux sans rien changer chez les autres.

Agents (Claude Code, Kiro)

CLAUDE.md et .kiro/steering/sas-pme.md font lire docs/ à chaque prompt. L'agent demande « A, B ou C ? » puis reste dans les dossiers de cette personne.

Sauvegardes — le local les rend plus faciles

Tout ce qui compte vit sur deux machines connues ; presque tout est reconstructible (les paquets sont publics). Ce qui ne l'est pas : notre jugement — verdicts, journal, clés.

Schéma 3-2-1

1Locale quotidienne : restic chiffré vers un NAS ou disque sur site, 30 jours
2Hors ligne hebdomadaire : disque USB chiffré débranché (contre un rançongiciel)
3Cloud : oui, en option, chiffré côté client (restic → S3 ou hébergeur français), clé détenue par la PME seule ; seule copie qui survit à un incendie
La clé privée de signature ne va jamais dans le cloud : deux copies hors ligne (USB chiffré au coffre, papier).

Dans le MVP (M2, C) : infra/sauvegarde.sh + test de restauration (effacer la base, restaurer, vérifier la chaîne du journal). Le cloud : feuille de route.

Après le hackathon

Priorité n° 1 : la plateforme d'intégration — installation en une commande, configuration automatique de pip/npm sur les serveurs, image d'appliance : le « seamless » chez une PME. Puis npm complet, Docker/Maven/NuGet, console multi-clients pour infogérants, télémétrie partagée.
